Requisitos da aplicação:
1. A API vai se integrar com a API da OpenAI para fazer uso dos modelos de LLM do gpt e também para fazer uso dos modelos de embeddings.

2. O contexto de dados para ser usado por IA nessa API são dados referentes a sprints de uma squad de desenvolvimento. As tarefas e sprints foram exportadas como json e o nosso modelo de IA vai operar em cima desses dados. Os dados vão estar dentro da pasta data/ e dentro dessa pasta, cada arquivo .json representa uma sprint, o nome do arquivo é o nome da sprint, cada sprint tem tarefas e subtarefas, que são representados pelo objetos json, uma sprints certamente terá várias tarefas e uma tarefa pode ou não conter várias subtarefas. A metodologia de desenvolvimento é o scrum. O objetivo da IA nessa nossa API é processar os dados das sprints, como veremos mais tarde, então esses json devem ser passados para ela de alguma forma (ou partes dele).

3. A API terá 2 rotas principais (é possível ter mais, mas o principal são essas 2 rotas), as quais vão concentrar as regras de negócio para a implementação da tarefa do PDF. Um rota será relacionada a resumo de tarefas e/ou sprints, ou seja, uma rota vai ser destinada a devolver resumos de tarefas, subtarefas ou sprints. Por exemplo, o usuário pode perguntar: “como está o andamento na sprints 75?” e o modelo deve fazer um resumo dos principais pontos e responder em tempo hábil, exempolo de resposta da IA: “a sprint está quase no fim, a maioria das tarefas foi desenvolvida, falta apenas X, Y Z tarefas, os devs A e B estão trabalhando nas tarefas C e D…”. Ou seja, a IA vai atuar como consultor, ele lê a pergunta do usuário, verifica onde deve pesquisar, consulta no local correto, processa os dados e volta a resposta de forma rápida. A outra rota será um RAG.

4. O RAG implementado em uma das rotas deve ter o seguinte: o usuário deve passar em quais sprints ele quer que a consulta ocorra (uma lista de sprints), caso a lista seja vazia, todas as sprints vão ser olhadas (RAG com base em todo banco de conhecimento em data/). Além disso, a requisição do usuário deve ter um parâmetro chamado “rank” que é um inteiro, e representa a quantidade de elementos a serem trazidos no RAG, por exemplo, um rank=3 significa que o usuário quer as 3 respostas mais próximas ao que ele pediu. Também deve haver um parâmetro com a mensagem do usuário e que será usada para fazer o RAG, por exemplo, a mensagem do usuário pode ser “funcionalidade de permissão de usuários no sistema” e a API deve fazer o RAG com base nesse texto e a base de dados que ela possui. Por fim, deve-se ter uma parâmetro que configura qual o tamanho do fragmento a ser respondido ao usuário, diferente de rank que diz quantos fragmentos serão retornados, esse parâmetro se refere ao tamanho do fragmento. Deve haver uma rota para o RAG, a qual deve ter as características necessárias para implementar os requisitos nesse documento.
